# Payment security rollout

The payment integration requires these server-side environment variables in local development and Vercel:

- `SESSION_SECRET`: a private random value of at least 32 bytes. Generate one locally with `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"`. Do not commit or paste it into chat.
- `ADMIN_EMAIL`: reserved email that public registration must not claim. Administrative authorization now uses the provisioned `User.isAdmin` role, not this email.
- `MERCADO_PAGO_ORDERS_ACCESS_TOKEN`: the production/test Access Token from the new Checkout Pro application configured for the Orders API.
- `MERCADO_PAGO_ORDERS_WEBHOOK_SECRET`: the signing secret from that application's Webhooks configuration for the `Order (Mercado Pago)` / `orders_v2` event.
- `MERCADO_PAGO_ACCESS_TOKEN` and `MERCADO_PAGO_WEBHOOK_SECRET`: retain the old Preferences credentials while legacy checkouts are still being reconciled.
- `NEXT_PUBLIC_BASE_URL`: the canonical HTTPS site URL in production.

Create the new Mercado Pago application as **Checkout Pro → API de Orders**. The new checkout route creates `/v1/orders`, redirects to its `checkout_url`, and uses the app-level `Order (Mercado Pago)` webhook. The old Preferences route and credentials remain available only for orders created before the switch.

Configure the new app's Webhooks separately for test and production, using the `Order (Mercado Pago)` event and `https://<site-domain>/api/mercadopago/verify-payment`. In Vercel Preview, set `MERCADO_PAGO_ORDERS_ACCESS_TOKEN` and `MERCADO_PAGO_ORDERS_WEBHOOK_SECRET` to the new app's test credentials/signature. Keep Production on its existing credentials until Preview has passed; then set the new app's production credentials in the same two variable names for Production. Do not replace the legacy variables until pending Preferences orders have been reconciled.

The Prisma additions are additive: the provider's order ID is nullable and indexed, so existing payment rows remain valid. The current `npm run build` runs `prisma db push` before generating the client; the SQL migration is also included for environments using Prisma Migrate.

Pending checkouts created before deployment remain verifiable only when Mercado Pago reports the exact existing catalog amount (ARS 3,000 or ARS 12,000) and the legacy user metadata/reference agree. The old client-provided quantity is not trusted.

New registrations store scrypt password hashes. Existing plaintext passwords are upgraded to scrypt after the account's next successful login, without changing the user's password. To migrate all existing rows at once, set the intended `DATABASE_URL` privately and run `npm run security:hash-legacy-passwords`; the script never prints passwords or hashes. Keep `SESSION_SECRET` stable; rotating it signs out all current sessions.

Full Mercado Pago refunds and chargebacks reverse the order's unspent token balance; any already-consumed amount becomes a token adjustment that future purchases settle before adding spendable tokens. Partial refunds are marked for manual reconciliation because token packs are indivisible.

## Audit fixes F01–F12 and H01

- Activation/expiry now share one transaction. Activation requires an inactive, debt-free user with a positive balance; expiry matches the exact activation timestamp observed.
- Balance-dependent calculations acquire `SELECT ... FOR UPDATE` on the owning `User` before reading or claiming orders/payments. Orders, Preferences, historical payments, activation and admin adjustments use the same lock order.
- Full refunds/chargebacks take precedence over partial-refund amounts. Historical `partial_refund_review` rows can transition to a final reversal once.
- `ProcessedPayment.creditedQuantity` records how many tokens were originally credited (including debt settlement). `NULL` preserves the historical meaning: the full recorded/catalog pack was credited. A reversal or partial review received before any credit creates a durable row with `creditedQuantity = 0`, blocking stale approvals without debiting unrelated purchases. Do not backfill historical rows to zero.
- Partial review never automatically removes tokens. If an operator performs a manual partial adjustment, they must record the remaining credited obligation in `creditedQuantity` in the same transaction as that adjustment; a later definitive reversal uses this remaining quantity. No automated partial-adjustment admin operation is provided.
- Approval helpers and webhooks use the same refund classification. Payments with a positive refunded amount cannot receive a fresh full-pack credit through manual verification.
- If Payments omits `preference_id`, the server fetches `/merchant_orders/{payment.order.id}` and requires the returned order ID, external reference, contained payment ID and preference to match. Missing/mismatched association still fails closed; an Orders API order cannot be claimed through the Preferences path.
- Webhook processing failures are persisted in `PaymentReconciliationIssue` and receive 503 to allow provider retries. Partial reviews are persisted and acknowledged. Successful retries resolve the issue. Authorized operators can inspect up to 100 unresolved issues through `GET /api/admin/payment-issues`; this endpoint never returns credentials or webhook payloads.
- Current clients persist a purchase `attemptId` per user/pack in session storage (with an in-memory fallback). The server derives a deterministic local order ID and uses that same ID as the Orders idempotency key. The original creation payload and checkout URL are saved, so retries reuse the original operation even if the account email or public URL changes. Old clients without `attemptId` remain compatible but do not gain cross-request creation idempotency until updated.
- After an unknown Preferences POST result, recovery searches `/checkout/preferences/search` by the local reference and retrieves the matched preference. It does not issue a blind second creation POST. An operation still in flight returns 409; unknown results remain pending for recovery and are visible in reconciliation issues. Recovered/known checkout URLs are reused.
- Manual reconciliation checks up to two pages of ten own local orders and two pages of historical payments. Already-processed recent payments do not hide older unprocessed payments. Local `paid` orders are queried remotely to detect missed refunds. Explicit order IDs remain owner-scoped. The client preserves unresolved return references; the manual button can fall back to the bounded own-order sweep.
- Admin authorization requires `User.isAdmin = true`. Registering an email, including casing variants or an injected role field, cannot assign this role. Public registration checks existing emails case-insensitively and reserves `ADMIN_EMAIL`.
- Logout stores a SHA-256 fingerprint of the revoked cookie in `RevokedSession`. All protected routes now await the revocation check. New cookies include a random session ID; pre-upgrade signed cookies can also be revoked. Another session is not revoked accidentally. Expired revocation entries are cleaned on logout.
- Database-backed atomic rate limits cover login (IP + account), registration (IP), checkout creation (account) and manual verification (account), across serverless instances. Actor identifiers are hashed. Request bodies are bounded by bytes even without `Content-Length` (16 KiB normally, 4 MiB for registration), receipt is limited to ten seconds, field lengths are bounded and Mercado Pago calls time out after ten seconds. Manual sweeps share a 20-second remote-query deadline; a final merchant-order association lookup can add up to ten seconds. Configure ingress/WAF limits as an additional deployment control. Expired rate-limit buckets can be deleted by an operator/maintenance job using `resetAt` without changing active buckets.
- Webhook signatures reject duplicate header keys, non-canonical hex and invalid timestamps. Both second and millisecond timestamps are supported. Replay policy accepts at most seven days of delayed delivery and five minutes of future skew; replays inside that window still consult current remote state and cannot duplicate credits. Confirm this delivery policy against the account's webhook retry behavior; older events can be reconciled through authenticated verification.

### Schema deployment

1. Expand the schema before activating new readers: `User.isAdmin`, `ProcessedPayment.creditedQuantity`, checkout creation/recovery fields and the reconciliation, revocation and rate-limit tables. Existing balances/payments are preserved. The current build's `prisma db push` creates these fields/tables but does not install SQL CHECK constraints.
2. Provision the verified existing admin account from a trusted operator shell: set `ADMIN_USER_ID` to that account's immutable database ID, then run `npm run security:grant-admin` with the intended database configured. The script changes only that account's role; it does not grant privileges from a public email claim. Existing admins will have no admin access until provisioned. Do not run this script against an unverified account.
3. For deployments using migrations, `20261117120000_payment_audit_fixes/migration.sql` also adds non-negative balance/debt constraints (`NOT VALID` preserves old rows for review while enforcing future writes). Do not blindly run `migrate deploy` against a database maintained only with `db push`: establish migration history first. If using `db push`, install the two CHECK constraints separately through the trusted database workflow after reviewing existing data.
4. Activate the patched app and drain old workers so balance writers consistently use the user lock. Verify checkout retry recovery, a signed webhook, manual verification, copied-cookie rejection after logout, and the provisioned admin role in an isolated environment before production cutover.

Production schema changes and role provisioning were not executed during local verification.

### Rollback / mixed versions

These schema additions are non-destructive and should be retained during rollback. Do not drop payment/reversal tombstones, revocations or original creation payloads. Once zero-credit tombstones exist, reverting to the pre-fix ledger is unsafe: it cannot distinguish a reviewed uncredited payment from a credited pack. Keep the patched ledger/auth modules and roll back UI/checkout enablement independently, or pause new checkouts while restoring a compatible version. Never overwrite balances or clear debt merely to make an older release run. All external writers/manual adjustments must follow the same user-row lock and account for `creditedQuantity`.

### Regression verification

Run `npm run test:payments`. The regression suite executes production modules with a deterministic in-memory Prisma-shaped adapter and per-user row locks. It covers concurrency, rollback, delayed approvals, partial-to-final reversals, historical NULL rows, verified merchant-order association, webhook recovery, manual sweeps, stable checkout retries, administrative roles, session revocation, body/rate limits and signature parsing. It uses no live database or credentials. Run a separate isolated PostgreSQL integration check before claiming real-database concurrency has been verified. Local gates are `prisma validate`, `prisma generate`, `tsc --noEmit`, `next build --webpack` and `git diff --check`; do not use the production `npm run build` as a local check because it executes `db push`.
